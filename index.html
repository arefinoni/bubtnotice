Engineering Insights

Behind the Technical Decisions

Common questions about the scraper design, performance considerations, and anti-ban safeguards.

Q. Why Selenium instead of pure BeautifulSoup?

The official BUBT portal uses client-side JavaScript to hydrate notice table rows via asynchronous requests. Pure HTTP libraries (e.g. requests) receive an empty table skeleton. Selenium drives a real Chromium engine and waits 8 seconds for the DOM to finish hydrating.

Q. Why convert PDFs into high-resolution images?

Most students view university updates on mobile devices. Downloading and opening a separate PDF viewer app causes friction. PyMuPDF renders all PDF pages into a single vertical 150 DPI PNG, allowing students to read the notice immediately inside Telegram.

Q. What does the keepalive workflow do?

GitHub automatically pauses scheduled GitHub Actions workflows on repositories that have had no git commits for 60 consecutive days. The keepalive.yml workflow triggers on the 1st of every month at 9:00 AM, committing a timestamp to keepalive.txt to keep the scraper active indefinitely.

Q. How are duplicates prevented across runs?

The bot stores unique detail page URLs in seen_notices.json. Before processing any notice, it checks this database in O(1) time. Whenever a new notice is sent, the file is automatically committed back to the repository via git push.

Q. Does the scraper overload the university server?

No. The scraper only queries the top 5 notices every 30 minutes (equivalent to 1 lightweight page request every half hour), and detail pages are only requested when a new notice is detected. It uses respectful headers and gentle delays.

Q. What happens if a notice has no attached PDF?

The system includes automatic graceful fallback: if no direct PDF URL is discovered on the detail page, it dispatches a formatted text message via Telegram's sendMessage endpoint with the notice title and direct portal URL.
